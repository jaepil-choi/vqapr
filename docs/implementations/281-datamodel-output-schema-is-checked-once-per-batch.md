## 왜 필요한가

실제 DW의 최대 공통 기간에서 DataModel은 2,096회 실행되어 419,686행을 만들었다. 한 실행이
반환하는 모든 행은 같은 여섯 필드를 갖지만, 기존 `normalize_rows`는 각 행의 각 필드명을 문자
단위로 다시 검사했다. 프로파일에서 `str.isspace`가 4,750만 회 호출되었고 출력 정규화와 검증이
누적 15.6초를 차지했다. 사용자 팩터 계산보다 반복적인 계약 확인이 더 큰 프로파일 비용이었다.

## 무엇을 바꾸는가

- 한 `normalize_rows` 호출 안에서 이미 통과한 필드명을 작은 집합에 기록함
- 같은 필드명이 다음 행에 나오면 빈 문자열·공백 문자 검사를 반복하지 않음
- 새로운 필드명은 어느 행에서 처음 나오든 기존과 똑같이 검사함

## 유지되는 계약

- 반환 행은 입력과 분리된 새 사전임
- 모든 값은 계속 `normalize_scalar`를 통과함
- NaN, 무한대, 지원하지 않는 객체는 계속 거절함
- 문자열이 아닌 키와 빈 문자열·공백이 있는 키는 계속 거절함
- DataModel의 정확한 필드 집합, 중복 종목, 요청하지 않은 종목 검사는 이후 단계에서 유지됨

## 대안과 판단

- Arrow 표를 DataModel의 새 출력 형식으로 받는 방법은 더 큰 절감 여지가 있으나 공개 계약과 사용자
  코드를 바꾸므로 이번 동일조건 비교에 사용하지 않음
- 행 복사를 생략하면 빠르지만 사용자 객체의 이후 변경이 기록에 영향을 줄 수 있어 거절함
- 스키마 이름만 같은 묶음 안에서 캐시하는 변경이 가장 작고 관찰 가능한 의미를 바꾸지 않음

## 검증

- 같은 키 객체가 세 행에 반복될 때 문자 검사가 한 번인지 집중 검사함
- 현재 `tests/data/test_shapes.py`의 모양·거절 계약을 함께 실행함
- 실제 DW 기준판과 후보의 DataModel 전체 결과 및 전략 결과를 전수 비교함
- 실제 DW DataModel 반복 중앙값은 15.936초에서 9.722초로 39.0% 줄었음
- 프로파일의 출력 정규화·검증 누적 시간은 15.619초에서 3.429초로 줄었음
- 같은 위치에서 다시 만든 DataModel 419,686행과 전략 결과 15개 표는 파일 해시까지 같음
- 집중 검사 21개, lint, typecheck, build가 통과함
- 기본 전체 검사는 1,764개 통과·7개 제외·2개 실패였고 두 실패는 손대지 않은 v0.15.0에서도
  재현함
- 느린 검사를 포함한 전체 검사는 1,792개 통과·7개 제외·3개 실패였음. 추가 실패는 저장소의
  `data/DW`가 없는 문제이며 실제 DW를 임시 위치에 연결해 해당 showcase를 따로 실행하면 통과함

## 남은 한계

- 값 하나하나의 유효성 검사는 여전히 Python에서 수행함
- 10분 이상 사용자 전략을 재현하지 못했으므로 장시간 사용자 코드에서의 전체 비율은 알 수 없음
- 열 단위 DataModel 출력은 별도 공개 API 설계와 호환성 검토가 필요함
