# vqapr 0.16.1 — every dataset enters by one door, a rows key is counted, and the roster stands apart from the data

Released 2026-09-14 from `develop`. The registration-cleanup campaign, records `280`–`284`, started from
the owner's questions while reading the 0.16.0 scenario stepper. A patch: no registered workspace, run
record or author import changes, and what a run computes does not change. One refusal status moves
(`dataset.source_mismatch` from `Transaction.register_dataset`, 409 → 400), two refusals go away
(a `rows` key that repeats or holds a null), one appears (`vqapr new <kind> --out X.yaml`), and the
sample writes its roster as its own declaration.

## A file is read where its reader lives (record `280`)

Reading a declaration file is not a domain rule: `read_declaration` (the YAML 1.2 loader) lives in
`workspace/registration.py`, `refuse_existing` in `cli/new.py`, and `domain/errors.py` opens no file.
`apply` is one function; the file it reports in refusals is set by a `with`.

## Every dataset enters by one door (record `281`)

`stage_measured` measures a dataset at the inspection bench, raises on a refusal, and stages the
**measured** card — for `register_dataset`, a declaration's `datasets:` and a run's published output
alike. "The registration and the source name different sources" is one rule (`mismatched_source`)
with one status, 400, wherever it is asked.

## A rows key is counted, not refused (record `282`)

`grain` already says whether a panel can be built. A panel grain still refuses a repeated or null
key axis — it would put two values in one cell. `grain: rows`, the vendor's long table, now
registers with repeated or null `key_fields` and the receipt says how many; a row-wise read orders
rows by `available_at`, the key, then every field, so a repeat comes back in one order every run.

## The roster refusal points at a road that exists (record `283`)

- `roster.absent` now says: `vqapr new instruments --instruments <ids...>` writes `instruments.py`
  (run it: it exports the tables) and `instruments.yaml`, then `vqapr register instruments.yaml` — or
  `vqapr.public.register_instruments(project_root, {id: kind})` does both.
- `vqapr check` lists `roster.absent` once. The freeze no longer asks what the `roster` judgment
  already answered.
- `vqapr new strategy|datamodel|compliance|exchange|instruments --out X.yaml` (or `.yml`) is refused
  with the name to pass instead: `--out` names the script, and its declaration was being written over it.

## The sample declares its roster apart from its data (record `284`)

`vqapr new sample` writes `instruments.yaml` beside `sample.yaml`. Data registers without a roster,
not every name in a dataset has to be an instrument, and only the roster's names can be ordered — so
the sample shows them as two declarations, and its `next` registers the roster first.

## Skills

`run-backtest` gains step 0: before a strategy's first run, register every id it may order — an
order for any other id fails the whole run, and `check` cannot see it coming. `register-dataset` and
`make-strategy` point there; `introduce-vqapr` walks the five commands of the sample.

## Migrating a 0.16.0 tree

- Nothing to register again.
- A script that registered a fresh `vqapr new sample` directory's `sample.yaml` alone registers its
  `instruments.yaml` first.
- A caller that handled `dataset.source_mismatch` from `Transaction.register_dataset` as 409 sees 400.
- Installed skills describe the old wording; install them again (`vqapr skill install --force`).
